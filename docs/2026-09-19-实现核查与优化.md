# 结账实现核查与优化（2026-09-19）

本次检查了监控、真实日志、购物袋入口、结账提交、通知和调度，并参考官方资料核对请求语义。变更只做离线验证，没有操作真实订单，也没有重启正在运行的监控。不能据此量化真实抢购成功率。

## 已完成的改动

| 原问题 | 当前行为 |
| --- | --- |
| 通知渠道串行发送，购买占用整个轮询线程 | 库存轮询、购买、通知分别执行；一个购买线程独占 Playwright。待付款通知有独立发送队列，避免排在库存消息后面。 |
| 同一门店持续有货时，重试被通知去重挡住 | 每次有效库存观察都更新候选；通知仍只在状态变化时发送。默认每个 SKU/门店每轮放货最多尝试 2 次，失败后至少等待 15 秒，并需要失败结束后的新样本。 |
| 一个候选售罄后，整个自动购买永久停止 | 只淘汰该 SKU/门店本轮候选，可尝试另一家允许的门店。只有完成购买、交给人工的 Review、已有提交记录等情况才停止新购买。 |
| 结账被限流后马上换门店再撞同一链路 | 当前尝试立即停止；购买线程至少冷却 120 秒，结账响应要求更长 Retry-After 时遵守该要求，之后只考虑新鲜的库存观察。 |
| 只拿列表第一家店，忽略部分偏好 | 候选必须满足 pickup.stores、autobuy.pickup_store_numbers 中配置的编号限制；编号支持列表、逗号分隔字符串和 null，门店名称不作为额外过滤条件；按 watch 顺序和编号顺序选择。失败后可选择其他有效候选，不并发改同一个购物袋。 |
| 各组全部查完才处理，后面的异常丢掉前面的货 | pickup 优先，每个最多 20 SKU 的批次返回即处理；发货状态最后查，失败不妨碍已发现的货。 |
| 未知/部分缺失库存被写成无货 | 撤回不能确认的购买候选，保留最后已知状态，不将查询失败当作一次新的放货。 |
| 库存样本排队后变旧 | 默认超过 30 秒不开始购买；请求开始时间及可用的 Age 参与样本年龄估计。日志记录 Age、Date、Cache-Control。缺少 Age 并不能证明数据新鲜。 |
| 快车道失败后刷新、回退网页再走一遍 | 结账向导只保留同源请求；快车道失败即结束当前尝试。商品选项、加购、登录、必要的购物袋入口、订单状态页和付款页仍保留。 |
| 删除网页操作时范围过大 | 购物袋 SKU、数量、来源已经确认，而接口入口未建立时，可用购物袋按钮建立会话；被拦截、型号不符、数量不明、提交后结果未知不走这条入口。 |
| 仅记“点击过加购”，重试信任过期的内存标记 | 每次尝试重新核对真实购物袋，精确匹配型号和数量；点击不再被当作加购成功。目标 part 不明确时停止。 |
| 提交状态只在内存里，重启可能重复购买 | 自动购买及手动 fastpath 共用操作系统文件锁。提交前将记录原子写入并 fsync；写失败不发送提交。提交后未明确确认的结果保持保护，即使进程退出也不能再次自动购买。 |
| 创建了订单但暂时没读到订单号，不发付款提醒 | 以服务端确认订单为准发送唤醒通知；采用最终订单 URL。结果不明时引导查看订单列表。 |
| 所配分期期数不存在时自动换成最长一期 | 只能使用配置的期数。普通支付在服务端不要求分期时不提交分期期数字段；付款标签必须明确匹配，不从空标签或多个近似选项猜测。 |
| HTTP 200 被过度信任 | 保留下一步模型检查，并拒绝明确的业务错误状态。购物袋未解析出来不能当作空袋。 |
| 实际请求尚未扣预算；max_interval 截短预算和 Retry-After | 每次发出监控请求前准入扣令牌；未发请求不扣费。Retry-After 支持秒数和 HTTP-date，端点冷却和预算等待均不受轮询最大间隔截短。 |
| 指数抖动造成较长查询空窗 | 改为目标间隔的 0.8–1.2 倍均匀抖动，保留预算、冷热时段和退避；不再声称随机分布能模拟真人或避免限流。 |
| 直到发现库存才检查登录、建立浏览器连接 | 默认启动时预检，空闲时每 600 秒检查一次；常驻连接由同一购买线程复用。需要验证码的页面保留供人工处理。可选产品页预热 180 秒后失效。 |
| launch、watch 同时自动购买且默认一直冲刺 | launch 只通知上架，不自行挑最便宜型号购买；run.sh 有启用型号时只运行 watch，否则运行 launch，显式 --sprint 才冲刺。两种状态文件分开。 |
| 多线程日志、状态文件写入容易交错或截断 | 日志文件写入加锁，终端分流按线程缓冲；库存状态采用原子写入。每次购买结束移除响应监听器。 |
| 依赖下限不能支持代码中的浏览器配置名称 | curl_cffi 下限提高到本机已验证的 0.16.3。 |

## 配置与操作

新增可选配置位于 config.example.json。已有配置无需补字段即可使用默认值：

```json
{
  "autobuy": {
    "preflight": true,
    "preflight_interval": 600,
    "warm_max_age": 180,
    "candidate_max_age": 30,
    "max_attempts_per_stock": 2,
    "retry_delay": 15
  }
}
```

订单提交记录为项目目录下的 order-attempt.json，锁文件为 .purchase.lock，均不提交 Git。锁保护同一项目目录下的购买进程；不能协调其他机器或其他 checkout 目录。用户在浏览器里手工修改购物袋也不受文件锁约束，因此提交前仍需要型号和数量核对。

```bash
# 查看提交记录
./.venv/bin/python -m hunter order-state

# 仅在人工核对 Apple 订单列表、确认允许下一次购买后执行
./.venv/bin/python -m hunter order-state --resolve
```

提交记录不自动过期：无法用等待时间证明上一单没有创建。确认创建、超时、断连、返回结账页而缺少明确无订单证据，都需要核对。Review 和 place_order=false 不发送订单提交。实际付款仍由用户完成，期限以订单页面为准。

令牌桶预算是进程内长期平均速率约束，允许 burst 突发，不是任意滑动一小时的精确上限，也不覆盖浏览器结账请求。run.sh 现在只启动一个监控进程，避免默认重复查询。

## 外部核查与实现依据

- [Playwright 线程要求](https://playwright.dev/python/docs/library#threading)：API 不支持跨线程共享，因此创建、预热、购买和关闭都在同一个购买线程。
- [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)：非幂等请求缺少未执行证据时不能自动重试。提交前落盘、进程锁和结果未知保护解决本地重复提交问题，不提供服务端幂等保证。
- [RFC 9110 Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)：服务端既可返回秒数，也可返回 HTTP-date；普通轮询间隔上限不应缩短这个等待。
- [RFC 9111 Age](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.1)：Age 是响应年龄估计；本地收到响应不等于库存刚生成。没有加入未经验证的随机防缓存参数。
- [Playwright APIRequestContext](https://playwright.dev/python/docs/api/class-apirequestcontext)：与浏览器共享 Cookie 不等于完整复现页面请求环境，保留已经跑通的页面 fetch。
- [Playwright hydration](https://playwright.dev/python/docs/navigations#hydration)、[网络响应等待](https://playwright.dev/python/docs/network#network-events)：点击可用不保证业务成功，因此加购必须核对服务端购物袋。当前保留产品页初始化与点击后的短等待；没有可靠的加购响应样本前，不猜测端点并盲目删除等待。
- [Apple 中国付款帮助](https://www.apple.com.cn/shop/help/payments)：普通支付宝/微信与分期有区别；统一 30 分钟付款承诺缺少依据，改为以订单页面为准。银行分期已有实测基础，普通支付新增分支只经过离线模型测试，仍需实际响应验证。
- [AWS 的 backoff/jitter 说明](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)讨论减少同步竞争，不保证真人行为或避免限流。
- [Akamai Bot Manager](https://www.akamai.com/products/bot-manager)不能证明本项目所有约 10 秒响应都来自同一风控策略。现有网络对照只能作为当时环境的观察，不据此自动换 IP、轮换身份或修改路由。
- 库存端点对照：[作者迁移记录](https://github.com/hteen/apple-store-helper/issues/131)、[Apple Pickup Watcher](https://github.com/ENCHIGO/apple-pickup-watcher)。这些是项目作者的一手材料，不是 Apple 私有接口的稳定契约，也未给出可直接替代已验证结账流程的更快公开接口。

## 验证与限制

完整离线 unittest 套件共 430 个测试通过；Python 编译、CLI 帮助、启动脚本语法和 git diff --check 通过。新增覆盖进程提交后退出、记录损坏/磁盘写失败、锁竞争、提交超时、关闭前禁止提交、缓慢通知、持续库存重试、新鲜度、门店限制、部分未知、批次异常、HTTP-date、预算准入、普通支付和必要网页入口。删除了直接复制旧内存判断的测试，改为调用实际流程核对。

没有进行真实加购/下单、支付、网络路由改动或运行中进程重启。实际配置里的付款方式、期数、型号和门店没有修改。银行分期成功路径的核心六步字段和顺序保留；新的普通支付分支、购物袋页面入口和后台运行方式仍需要后续真实环境观察。

没有继续盲改的部分：Apple 私有接口替换、支付字段扩展、减少产品页初始化等待、提前锁库存的假设、所谓解除每步 10 秒延迟的方法。需要新的脱敏响应与耗时证据再判断，不能用离线测试伪造真实成功率。


## 用户复核后的修正

- 登录前后的结账入口共用 `_enter_checkout`，购物袋准备、接口入口及网页入口的 `Blocked` 统一在 `_drive` 转为不可立即重试的结果，携带至少 120 秒（或更长 Retry-After）的全候选冷却。购买线程也保留类型检查，预检与预热在冷却期间暂停。
- `prepare_bag` 读取购物袋和删除条目均检查 403/429/503/541，不再将限流归类为普通模型解析失败。预热体检不吞掉这些异常。
- 普通购买与预热 `fire()` 共用清袋后的产品页刷新及折抵/AppleCare 重选逻辑；保留目标商品时不额外刷新或加购。预热初始化阶段清袋也会重建产品页。
- `pickup_stores` / `pickup_store_name` 只保留名称展示兼容性，不否决编号命中。编号配置与 AutoBuy 共用 `_store_list` 解析。
- 启用 pickup 时，Pacer 的成功/失败反馈仅跟随 pickup；availability 由自己的端点熔断器控制。pickup 本轮未实际成功查询时返回 False，不触发 `on_ok()`。关闭 pickup 后，availability 才成为 Pacer 的主反馈来源。

新增 11 个回归测试覆盖以上路径，包括实际购买线程冷却、真实 AppleClient/Pacer 编排配模拟响应（无网络请求），以及登录后 EntryUnavailable → Blocked 的完整异常传播链。
